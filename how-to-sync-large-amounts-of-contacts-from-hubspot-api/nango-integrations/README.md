# Nango integrations — HubSpot contacts sync

A [Nango](https://nango.dev) sync function that incrementally syncs HubSpot contacts and slides past HubSpot's 10,000-result search cap with a two-phase strategy.

## What's inside

- [`hubspot/syncs/fetch-contacts.ts`](hubspot/syncs/fetch-contacts.ts) — the sync. Phase one bootstraps the cache via `GET /crm/v3/objects/contacts` and the `after` cursor (no 10k cap). Phase two takes over with `POST /crm/v3/objects/contacts/search` filtering on `lastmodifieddate GT <watermark>`. State for both phases lives in a Nango checkpoint, so each scheduled run resumes cleanly past the cap.
- [`hubspot/tests/`](hubspot/tests) — recorded mocks and a Vitest test generated by `nango generate:tests`.
- [`index.ts`](index.ts) — Nango's entry point. Side-effect imports for every action/sync.

## Prerequisites

- Node.js ≥ 20
- A free Nango account (https://app.nango.dev)
- The HubSpot integration enabled in your Nango environment

## Setup

```bash
npm install
cp .env.example .env
# Open .env and paste your Nango dev secret key
```

## Develop locally

```bash
# Type-check + compile
npx nango compile

# Dry-run against a real connection (no records are written to your DB)
npx nango dryrun fetch-contacts <connection-id> \
  --integration-id hubspot \
  --validate -e dev --no-interactive --auto-confirm
```

To simulate a resumed run, pass a `--checkpoint`:

```bash
# Resume mid-initial phase
npx nango dryrun fetch-contacts <connection-id> --integration-id hubspot \
  --validate -e dev --no-interactive --auto-confirm \
  --checkpoint '{"phase":"initial","after":"<cursor>","lastmodifieddate":"2026-05-03T16:00:00.000Z"}'

# Resume an incremental run
npx nango dryrun fetch-contacts <connection-id> --integration-id hubspot \
  --validate -e dev --no-interactive --auto-confirm \
  --checkpoint '{"phase":"incremental","after":"","lastmodifieddate":"2026-03-01T00:00:00.000Z"}'
```

## Run tests

```bash
npx nango generate:tests   # only needed once (or after editing the sync)
npm test
```

## Deploy

```bash
npx nango deploy dev
```

Once deployed, create a HubSpot connection (use the demo app in [`../demo-app`](../demo-app) for a one-click flow) and the sync will start running on its hourly schedule. Webhooks fire after every run.

### What `deploy` actually does

`nango deploy` doesn't use a config file — it derives the destination from the filesystem and your secret key:

- **Which integration the sync attaches to** comes from the **top-level folder name**. `hubspot/syncs/fetch-contacts.ts` → `providerConfigKey: "hubspot"`. An integration with that exact key must already exist in your Nango dashboard before you deploy. Create it once via *Integrations → Configure new integration → HubSpot*, and confirm the "Unique Key" field is `hubspot`.
- **The sync's name** is the filename without `.ts` (`fetch-contacts`).
- **Schedule, autoStart, models, description** come from the `createSync({ … })` arguments inside the `.ts` file.
- **Which account + environment** is determined by `NANGO_SECRET_KEY_DEV` in `.env`. The `dev` argument on the CLI is just confirming the environment label — it must match the one the key belongs to.

## Two-phase strategy at a glance

1. **Initial** — `GET /crm/v3/objects/contacts?after=…&limit=100`. Saves the cursor and the highest `lastmodifieddate` seen on every page. When `paging.next.after` is missing, the checkpoint flips to `phase: 'incremental'`.
2. **Incremental** — `POST /crm/v3/objects/contacts/search` with `filterGroups: [{ filters: [{ propertyName: 'lastmodifieddate', operator: 'GT', value: <watermark> }] }]`, sorted ASC. The filter watermark stays constant for the duration of one run (HubSpot's `after` cursor is only valid for the originating query); the saved watermark advances per page so the next scheduled run picks up cleanly. If HubSpot 400s past 10k, the next run starts with a higher watermark and slides past it.

The full reasoning is inline in [`fetch-contacts.ts`](hubspot/syncs/fetch-contacts.ts).
